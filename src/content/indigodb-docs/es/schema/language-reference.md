Todo proyecto IndigoDB gira en torno a un archivo de esquema `.indigo` (por defecto `schema.indigo`). El lenguaje combina **bloques `Table` y `TableGroup` al estilo dbdiagram** con **atributos `@` y `@@` al estilo Prisma** para que el tipado del ORM, las migraciones, los diagramas ER y la documentación compartan una sola definición.

## Bloques de Nivel Superior

Un esquema `.indigo` admite cinco declaraciones principales:

1. `datasource`: Configuración de conexión a la base de datos.
2. `generator`: Destino de generación del cliente ORM en TypeScript.
3. `enum`: Definiciones de tipos enumerados en PostgreSQL.
4. `Table`: Modelos/tablas con columnas, relaciones, índices, políticas RLS y directivas realtime.
5. `TableGroup`: Agrupaciones visuales con color para el diseñador ER de Studio.

Los comentarios de línea utilizan `//`.

## `datasource` y `generator`

IndigoDB está orientado a **PostgreSQL** (`provider = "postgresql"` es validado por el compilador):

```indigo
datasource db {
  provider = "postgresql"
  url = env("DATABASE_URL")
}

generator client {
  provider = "indigodb-client-ts"
  output = "src/generated/indigo.ts"
}
```

- `datasource.url` admite `env("NOMBRE_VARIABLE")` (recomendado) o una cadena de conexión literal.
- `generator.output` define la ruta donde `indigodb generate` emite el cliente TypeScript (por defecto `src/generated/indigo.ts`).

## Tipos Escalares y Mapeo de Dialectos

IndigoDB soporta nueve tipos escalares definidos en [`@indigodb/ast`](https://www.npmjs.com/package/@indigodb/ast) (`ScalarType`):

| Tipo `.indigo` | DDL PostgreSQL por Defecto | Tipo TypeScript Generado | Notas |
| :--- | :--- | :--- | :--- |
| `String` | `text` | `string` | Sobrescribible con `@db.VarChar(n)` o `@db.Uuid` |
| `Int` | `integer` | `number` | Con `@default(autoincrement())` emite `integer GENERATED BY DEFAULT AS IDENTITY` |
| `BigInt` | `bigint` | `string` | Tipado como `string` en JS para preservar precisión int8 de `pg` |
| `Float` | `double precision` | `number` | Admite `@db.Numeric` / `@db.Numeric(p, s)` |
| `Decimal` | `numeric` | `string` | Admite `@db.Numeric` / `@db.Numeric(p, s)`; `string` preserva precisión arbitraria |
| `Boolean` | `boolean` | `boolean` | Literales `@default(true)` / `@default(false)` |
| `DateTime` | `timestamptz` | `Date` | Admite `@default(now())` (`DEFAULT now()`) |
| `Json` | `jsonb` | `unknown` | Admite `JsonFilter` (`path`, `jsonContains`) en `where` |
| `Bytes` | `bytea` | `Buffer` | Cargas binarias |

### Modificadores de Campo

- **Opcional / Nulable (`?`)**: `bio String?` genera una columna que permite `NULL` y tipo `string | null` en TypeScript.
- **Lista (`[]`)**: Se utiliza en el lado inverso de relaciones uno-a-muchos (por ejemplo `posts Post[]`).

## Enums y Mapeo de Valores

Los enums compilan hacia declaraciones `CREATE TYPE ... AS ENUM (...)` en PostgreSQL y uniones literales en TypeScript:

```indigo
enum OrderStatus {
  PENDING   @map("pending")
  PAID      @map("paid")
  CANCELLED @map("cancelled")
}
```

- `@map("...")` sobre un miembro del enum desacopla el identificador TypeScript (`PENDING`) de la etiqueta física en PostgreSQL (`'pending'`).
- Tanto el migrador como el generador resuelven `@default(PENDING)` usando automáticamente la etiqueta física (`'pending'::"OrderStatus"`).

## Atributos de Campo

El compilador aplica una lista blanca estricta (`crates/indigo-compiler/src/rules.rs`): cualquier atributo desconocido o argumento mal escrito falla inmediatamente con línea y columna 1-based.

| Atributo | Destino | Descripción |
| :--- | :--- | :--- |
| `@id` | Campo escalar / enum | Marca la clave primaria. Repite `@id` en varios campos para clave primaria compuesta |
| `@unique` | Campo escalar / enum | Crea una restricción única de una columna (`<table>_<col>_key`) |
| `@default(expr)` | Campo escalar / enum | Literales (`"x"`, `0`, `true`), miembros de enum (`USER`) o funciones: `autoincrement()`, `now()`, `uuid()`, `cuid()` |
| `@map("col_name")` | Campo | Mapea el nombre en TypeScript (`createdAt`) a la columna física (`created_at`) |
| `@note("texto")` | Campo | Nota de documentación visible en Studio Docs y en el inspector ER |
| `@relation(...)` | Campo de modelo | Declara una relación por clave foránea |
| `@db.<Tipo>(...)` | Campo escalar | Tipo nativo PostgreSQL (`@db.VarChar(n)`, `@db.Uuid`, `@db.Numeric`) |

> Nota sobre `@default(cuid())`: `cuid()` es aceptado por el compilador sin emitir cláusula `DEFAULT` en SQL (pensado para generación en la aplicación). `@default(uuid())` emite `DEFAULT gen_random_uuid()` y `@default(autoincrement())` emite `GENERATED BY DEFAULT AS IDENTITY`.

## Relaciones y Acciones Referenciales

Declara `@relation(fields: [...], references: [...])` en la tabla que posee la clave foránea y el tipo del modelo relacionado en el lado inverso:

```indigo
Table User {
  id      Int      @id @default(autoincrement())
  profile Profile?
  posts   Post[]
}

Table Profile {
  id     Int    @id @default(autoincrement())
  userId Int    @unique @map("user_id")
  user   User   @relation(fields: [userId], references: [id], onDelete: Cascade)
}

Table Post {
  id       Int    @id @default(autoincrement())
  authorId Int    @map("author_id")
  author   User   @relation(fields: [authorId], references: [id], onDelete: Restrict, onUpdate: Cascade)

  @@index([authorId])
}
```

### Desambiguar Múltiples Relaciones

Cuando dos modelos comparten más de una relación, nombra cada par con una cadena inicial en `@relation("Nombre", ...)`:

```indigo
Table User {
  id            Int    @id @default(autoincrement())
  authoredPosts Post[] @relation("Author")
  reviewedPosts Post[] @relation("Reviewer")
}

Table Post {
  id         Int   @id @default(autoincrement())
  authorId   Int
  reviewerId Int?
  author     User  @relation("Author", fields: [authorId], references: [id])
  reviewer   User? @relation("Reviewer", fields: [reviewerId], references: [id], onDelete: SetNull)
}
```

### Acciones Referenciales Admitidas

Tanto `onDelete` como `onUpdate` aceptan el vocabulario PascalCase exacto:

| En `.indigo` | DDL PostgreSQL |
| :--- | :--- |
| `Cascade` | `CASCADE` |
| `Restrict` | `RESTRICT` |
| `SetNull` | `SET NULL` |
| `SetDefault` | `SET DEFAULT` |
| `NoAction` | `NO ACTION` |

> Nota: El compilador resuelve `onDelete` y `onUpdate` en la IR `ForeignKey`; actualmente `@indigodb/migrator` emite `ON DELETE` directamente en el DDL generado.

## Atributos de Bloque (`Table`)

| Atributo | Descripción |
| :--- | :--- |
| `@@map("nombre_tabla")` | Mapea un modelo PascalCase a otro nombre físico en PostgreSQL |
| `@@note("texto")` | Nota de documentación a nivel de tabla para Studio Docs |
| `@@index([...], ...)` | Índice secundario (admite `name:`, `type:`, `where:`, `expression:`) |
| `@@unique([...], ...)` | Restricción única compuesta, parcial o por expresión (solo `btree`) |
| `@@allow(acción, cond)` | Política declarativa PostgreSQL Row-Level Security (`read`, `create`, `update`, `delete`, `write`, `all`) |
| `@@realtime` / `@@realtime(columns: [...])` | Emite eventos WAL `pgoutput` con lista blanca opcional de columnas |

## Agrupación Visual (`TableGroup`)

`TableGroup` organiza las tablas en dominios de color en el diseñador ER de IndigoDB Studio sin afectar el DDL SQL:

```indigo
TableGroup "Facturación y Pedidos" {
  color = "#38bdf8"

  Invoice
  Payment
  Subscription
}
```

## Impresión de Esquema (`printSchema`)

`@indigodb/core` exporta `printSchema(resolved, options)` como función inversa determinista de `parse` + `resolve`, utilizada por `indigodb db pull` para formatear esquemas introspectados en texto `.indigo`.
