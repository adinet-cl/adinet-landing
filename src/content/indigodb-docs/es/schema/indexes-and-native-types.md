Además de tablas y claves foráneas estándar, `.indigo` permite modelar almacenamiento físico específico de PostgreSQL, métodos de acceso para índices, políticas Row-Level Security (RLS) y replicación lógica filtrada por columna.

## Tipos Nativos PostgreSQL (`@db.*`)

Usa `@db.<Tipo>` cuando necesites un tipo SQL más específico que el mapeo escalar por defecto (`text`, `numeric`, etc.). El compilador valida compatibilidad y aridad estrictamente:

| Atributo | Escalares Compatibles | Aridad | DDL PostgreSQL Emitido |
| :--- | :--- | :--- | :--- |
| `@db.VarChar(n)` | `String` | 1 entero | `VARCHAR(n)` |
| `@db.Uuid` | `String` | 0 argumentos | `UUID` |
| `@db.Numeric` / `@db.Numeric(p, s)` | `Decimal`, `Float` | 0 o 2 enteros | `NUMERIC` o `NUMERIC(p,s)` |

```indigo
Table Product {
  id    String  @id @db.Uuid @default(uuid())
  sku   String  @unique @db.VarChar(64)
  price Decimal @db.Numeric(12, 2)
}
```

> Regla de precedencia: Si una columna declara `@default(autoincrement())`, la cláusula `GENERATED BY DEFAULT AS IDENTITY` (`integer` o `bigint`) prevalece sobre `@db.*`.

## Índices (`@@index` y `@@unique`)

Tanto `@@index` como `@@unique` aceptan un arreglo de campos del modelo (o `[]` en índices por expresión) junto con los argumentos nombrados opcionales `name`, `type`, `where` y `expression`.

### Índices Nombrados y Tipados

```indigo
Table Article {
  id       String @id @db.Uuid
  slug     String
  tags     Json
  location String

  @@index([slug], name: "article_slug_hash_idx", type: hash)
  @@index([tags], type: gin)
  @@unique([slug], name: "article_slug_key", type: btree)
}
```

- **Métodos `type:` admitidos**: `btree` (por defecto), `gin`, `gist`, `hash`.
- **Restricción en `@@unique`**: Los índices únicos solo admiten `btree`.
- **Límite de identificadores**: Todo `name:` explícito debe tener entre 1 y 63 bytes (`NAMEDATALEN`), sin comillas ni caracteres de control, y sin colisionar con otros nombres explícitos o autogenerados (`<table>_<cols>_idx` / `<table>_<cols>_key`) en la misma tabla.

### Índices Parciales y por Expresión

Usa `where:` para índices parciales y `expression:` (con lista de columnas vacía `[]` y `name:` obligatorio) para índices sobre expresiones SQL:

```indigo
Table Account {
  id        Int       @id @default(autoincrement())
  email     String
  deletedAt DateTime? @map("deleted_at")
  metadata  Json

  // Índice parcial solo para cuentas activas
  @@index([email], where: "deleted_at IS NULL")

  // Índice único parcial con nombre explícito
  @@unique([email], name: "account_active_email_key", where: "deleted_at IS NULL")

  // Índice por expresión (requiere [] y name:)
  @@index([], name: "account_lower_email_idx", expression: "lower(email)")

  // Índice único parcial + expresión
  @@unique([], name: "account_active_lower_email_key", expression: "lower(email)", where: "deleted_at IS NULL")

  // Índice GIN sobre expresión JSONB
  @@index([], name: "account_meta_tags_gin", type: gin, expression: "(metadata -> 'tags')")
}
```

> **Nota sobre `upsert`**: Los índices únicos parciales y por expresión se excluyen de `ModelWhereUniqueInput` y de los objetivos `ON CONFLICT` de `upsert`, ya que PostgreSQL no admite inferir un índice filtrado en un `ON CONFLICT (cols)` incondicional.

## Row-Level Security Declarativo (`@@allow`)

Declara reglas de aislamiento por propietario o tenant directamente en la tabla con `@@allow(acción, condición)`:

```indigo
Table Document {
  id       Int     @id @default(autoincrement())
  title    String
  ownerId  Int     @map("owner_id")
  isPublic Boolean @default(false) @map("is_public")

  @@allow(read, auth.userId == this.ownerId)
  @@allow(read, this.isPublic == true)
  @@allow([create, update, delete], auth.userId == this.ownerId)
}
```

### Gramática y Expansión

- **Acciones canónicas**: `read`, `create`, `update`, `delete` (identificador individual o arreglo `[create, update]`).
- **Alias de conveniencia**:
  - `write` se expande en compilación a `create`, `update` y `delete`.
  - `all` se expande a `create`, `read`, `update` y `delete`.
- **Múltiples reglas por acción**: Se combinan nativamente con semántica `OR` en las políticas `CREATE POLICY` de PostgreSQL.
- **Operandos admitidos**: Igualdad `==` entre `this.<campo>` (resuelto a `dbName`), `auth.userId` o literales `string` / `number` / `boolean`.

### Cómo Aplica IndigoDB `@@allow` en PostgreSQL

1. `@indigodb/migrator` emite `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`, `ALTER TABLE ... FORCE ROW LEVEL SECURITY;` y políticas `CREATE POLICY` basadas en `current_setting('app.user_id', true)`.
2. El migrador deriva automáticamente el cast SQL exacto (`::integer`, `::uuid`, `::text`, etc.) mediante `columnSqlType(column)`.
3. En tu backend, [`db.$auth({ userId }, async (tx) => ...)`](/indigodb/orm/transactions-rls-and-adapters#row-level-security-con-auth) abre una transacción exclusiva y ejecuta `SELECT set_config('app.user_id', $1, true)` (parametrizado y local a la transacción), evitando fugas de identidad al reciclar conexiones del pool.

## Proyección de Columnas en Tiempo Real (`@@realtime`)

Marca cualquier tabla con `@id` usando `@@realtime` para emitir cambios vía `@indigodb/realtime`:

```indigo
Table User {
  id           String @id @db.Uuid
  email        String @map("email_address")
  passwordHash String
  status       String

  // Solo id y email llegan a payloads/log; passwordHash se filtra antes del fan-out
  @@realtime(columns: [id, email])
}
```

- **`@@realtime` sin argumentos**: Emite todas las columnas en `new` / `old` (en `GET /api/realtime/log` y listeners `engine.on("change")`).
- **`@@realtime(columns: [...])`**: Recorta `new` y `old` en origen dentro de `WalSource` / `PgNotifySource` antes de llegar al log o suscriptores; cualquier columna futura añadida a la tabla queda excluida por defecto (fail-closed).
- **`@@realtime(columns: [])`**: Sintaxis válida para notificaciones solo de identidad (`pk`).
